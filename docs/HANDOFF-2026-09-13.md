### 2.2 Rótulo de impacto (a base para a próxima tarefa)

- **`FormSurfaceService`** — lê do HTML o que a página coleta: `<form`,
  `type=password`, campos de PII (e-mail/tel/CPF/CNPJ), campos de cartão
  (`autocomplete="cc-*"`, CVV). **Custo zero de rede**: o `HttpFetchService` já
  baixava o corpo para a CSP de `<meta>` e o descartava.
- **`ImpactLabelService`** — função pura sobre `ScanResult`. Quatro níveis, o mais
  alto vence: `SHOWCASE → CONTACT → ACCOUNT → PAYMENT`.
- **Não entra no score.** Eixo paralelo, de propósito — mexer na nota quebraria as
  séries históricas e a detecção de mudança por caminho.

Já disponíveis no JSON do scan: `ScanResult.impact` e `ScanResult.formSurface`.

> **Decisão importante:** `inputSurfaceDetected` **não** foi substituído. Ele é
> `hasQueryParams(url)` e gateia os probes de XSS, SQLi e path traversal — os três
> precisam de query string. Trocá-lo por "tem formulário" faria os probes rodarem
> em página sem `?`, virando no-op marcado como executado.

## 3. Próxima tarefa — UI do rótulo de impacto

O backend já entrega o dado. **Falta só a interface.** O usuário quer que todos
consigam ver o risco do site, não só o número.

### 3.1 Onde o rótulo deve aparecer

| # | Superfície | Onde no código | Por quê |
|---|---|---|---|
| 1 | Barra lateral do scanner, ao lado de `56/100 MEDIUM` | `App.tsx`, perto de `badgeHost` / `badgePath` | é o primeiro lugar que o olho vai |
| 2 | Card de resumo (`MEDIUM` + URL + HTTP) | mesmo bloco do gauge | dá contexto à nota |
| 3 | **Aba Caminhos (Histórico)** — rótulo **por caminho** | aba criada nesta sessão | é onde brilha: home = `VITRINE`, `/checkout` = `PAGAMENTO` no mesmo domínio |
| 4 | Visão Geral — ordenar/filtrar por impacto | `ChangesPage`, aba overview | filtro de prospect: quem merece reunião sobe |
| 5 | PDF, na caixa de resumo ao lado do score | `PdfReportService.summaryBox` | o laudo vai para o cliente |

### 3.2 Textos (o usuário já validou)

| Nível | Significa | Frase |
|---|---|---|
| `SHOWCASE` | Não coleta nada. Informativo, WhatsApp, sem formulário | "Frágil, sem dado em risco" |
| `CONTACT` | Coleta dado, sem conta: formulário, e-mail, telefone, CPF | "Coleta dado pessoal sem proteção" |
| `ACCOUNT` | Área autenticada: sessão, login, token | "Conta de cliente exposta" |
| `PAYMENT` | Checkout, cartão, plataforma de pagamento | "Dado de pagamento em risco" |

Enum em inglês (`SHOWCASE/CONTACT/ACCOUNT/PAYMENT`, igual a `RiskLevel`); os
rótulos PT/EN vão para `src/i18n/catalog.ts` — **sempre nos dois catálogos**, senão
o `tsc -b` acusa chave duplicada ou o teste de paridade falha.

### 3.3 Cor — não reaproveitar a do score

O score já usa verde/amarelo/vermelho por severidade. O impacto é **outro eixo**:
se usar a mesma escala, os dois se confundem. Sugestão: escala neutra (cinza →
âmbar → laranja → vermelho) ou só um selo com ícone, deixando a cor forte para a
severidade. **Decisão de design, confirmar com o usuário.**

### 3.4 Ambiguidade a resolver antes de codar

O usuário escreveu *"deixar possibilitado que todos os usuários possam ver o risco
do site"*. Duas leituras:

- **(a)** todo usuário do produto vê o rótulo (sem trava de plano) — provável;
- **(b)** expor no **badge público / página de status**, visível na internet.

**(b) é sensível**: publicar "PAYMENT + score 11" no site de um terceiro é outra
conversa. **Perguntar antes de implementar.**

## 5. Armadilhas desta sessão — leia antes de mexer

| Armadilha | O que acontece | O que fazer |
|---|---|---|
| **`tsc --noEmit` não verifica nada** | O tsconfig da raiz só tem `references`; o comando sai limpo sem analisar código. Uma edição minha vazou para outra tabela e ele não acusou | Usar `npm run build` ou `npx tsc -b` |
| **`sed` com `\|` e regex Java** | `\|` vira alternação no GNU sed; `\\s` colapsa para `\s` (escape ilegal em Java). Falhou 3× nesta sessão, inclusive silenciosamente | Usar `awk` com `index($0, "literal")` ou a ferramenta Edit |
| **Heredoc grande no Bash** | Arquivo > ~8KB trunca e quebra o heredoc | Usar a ferramenta Write |
| **`ddl-auto` + coluna `NOT NULL`** | Postgres recusa `ADD COLUMN NOT NULL` em tabela com linhas; Hibernate loga e sobe assim mesmo — a coluna some e toda query quebra | `@Column(nullable = false, columnDefinition = "BOOLEAN DEFAULT FALSE")` |
| **`ddl-auto` + enum** | Não atualiza o `CHECK` de `audit_logs.action`. Adicionar valor a `AuditAction` quebra inserts | Não adicionar sem rodar o SQL de `deploy/` |
| **Ordem de deploy** | Backend **sempre** antes do Frontend | Frontend novo contra backend velho perde parâmetros (`?path=`) e endpoints (`/history/paths`, `/user/timezone`) |

### 5.1 Disciplina de teste adotada

Todo teste desta sessão foi validado **rodando com o defeito de volta** e
confirmando a falha. Isso pegou um teste meu que não cobria nada: usava
`__cf_bm`/`_cfuvid`/`_ga`, que não contêm fragmento de sessão, então passava com ou
sem a exclusão. O teste corrigido usa `_hjSession_1873402` (Hotjar) e
`ajs_user_id` (Segment), que **colidem de verdade** — e revelou que a lista
comparava por igualdade, nunca casando nomes com sufixo dinâmico.

**Não confie num teste verde que você não viu falhar.**

## 6. Contexto de negócio (afeta decisões de produto)

O usuário está vendendo o sistema. Encontra prospects pelo Google Maps, e a maioria
são **sites institucionais** — que pontuam baixo mas não têm o que perder. Foi
exatamente o que motivou o rótulo de impacto.

Conclusão que orientou o desenho: foque em sites que **tocam dado de cliente** e
cujo dono **controla o conserto**. Loja em plataforma SaaS (Tiendanube, VTEX) é
armadilha — os cabeçalhos do checkout são da plataforma, o lojista não consegue
corrigir, e apontar isso mata a venda.

Há um comparativo home-vs-checkout publicado como artifact (arrazzestore), com a
divisão "responsabilidade da plataforma vs. da loja" — modelo para futuros laudos
comerciais.
